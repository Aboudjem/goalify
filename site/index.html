The problem

Claude said done. It wasn't.

Long jobs fail in two boring ways. The agent stops every hour to ask you something, or it says "all done" while a test is still red. goalify fixes both before the run even starts.

WITHOUT GOALIFY

  • It stops at 3am to ask which database you meant
  • The plan lives in a chat that /clear wipes
  • It invents an npm test your repo doesn't have
  • "Done!" means it said so
  • You find the gaps the next morning

WITH GOALIFY

  • Every question is asked once, up front
  • The plan is a file the fresh session re-reads every loop
  • Checks come from your repo and your CI
  • "Done" means the last turn quoted the passing output
  • One command re-runs the checks and hands you a receipt
How it works

All the thinking first. Then it just works.

goalify only prepares. Claude Code's own /goal does the running. goalify makes sure nothing is left for the run to ask about.

STEP 1

Homework

Can this even work? It reads the docs, checks the repo and finds your real test commands.

STEP 2

Questions, once

A few real choices, asked in one batch. That's the last time it bugs you.

STEP 3

Brief + condition

A brief the run works from, and one short line for /goal that says what proof looks like.

STEP 4

/clear, paste, walk away

A fresh session spends all of its context on your job, not on your chat history.

Why it can run for days

Zero interruptions, because there's nothing left to ask.

The research, your decisions and the finish line are all locked in before you hit /clear. After that, the run works, checks, fixes and repeats. A separate evaluator reads the transcript after every turn and lets it stop only when the proof is there, or when it hits the turn cap you set.

Questions

Good to know

Does goalify do the task?

No. goalify never does the task. It writes the brief and the condition, and it only runs your checks when you ask (/goalify verify). The work happens in the fresh session you start with /goal.

Why can't I just hand /goal my plan file?

Because /goal takes a condition string, not a file path. The evaluator behind it has no tools and can't open files, so a path would just be a sentence it can never check. goalify puts the brief's path inside a real condition instead.

Is a stopped run proof that it's done?

No, and goalify says so. The evaluator can also end a run by deciding the goal can't be reached. Run /goalify verify on the brief to re-run its checks and get a receipt.

What does it cost?

goalify is free and MIT licensed. It never guesses a dollar or token figure for your run. The turn cap in the condition is the control you get.

Does it phone home?

No. No server, no runtime dependency, no network call. The scripts are plain Python standard library and the preview page makes no outside requests.

Does it work with Codex?

Yes. Codex has its own /goal that also takes an inline objective, so goalify prints the Codex form too. Codex treats the objective as data, so the finish line carries over but the process rules in the brief may not.
